# Repo Risk Agent

**A due-diligence agent that assesses a codebase's risk for a freelance engineer deciding whether to take on a project, before they quote a price or timeline.**

## Who this is for

Freelance software engineers who get handed an unfamiliar client codebase and have to decide, often within a day, whether it's healthy or a tech-debt trap — and what to charge if they take it on.

## The bottleneck

Doing this properly means cloning the repo, trying to install and build it, running its test suite, checking dependencies for known vulnerabilities, scanning for committed secrets, and reading enough of the structure to spot god-files or missing tests. That's an hour or more of manual work per prospective project, and under time pressure it's easy to skip a step — or to skim the code, form a gut impression, and underquote a project that turns out to be barely buildable.

The common shortcut today is exactly the wrong one: paste some files into an LLM and ask "does this look okay?" That produces a confident-sounding answer that has not actually verified anything — the model has no way to know if the tests really pass or the dependencies are really vulnerable, but it will often say so anyway.

## What this does

Two systems assess the same repos and produce the same structured report (`risk_score`, `effort_multiplier`, evidence-backed `red_flags`, `clarifying_questions`, `go_no_go`):

- **`baseline/`** — one LLM call, zero tools. A bounded dump of files (README, manifests, CI config, largest source files, sample tests) is handed to the model with an explicit instruction not to assert build/test/vulnerability status unless a file directly states it. This is the realistic "basic way to handle the task" the shortcut above actually looks like.
- **`agent/`** — the same model, but with tools that *actually run* verification inside a disposable Docker sandbox: install/build, test suite, `dependency_audit` (npm audit / pip-audit), `run_linter_or_complexity` (ruff+radon / eslint), and `scan_secrets`. A verification contract in its system prompt requires every red flag to cite the tool call or file line it came from — unverified claims go into `clarifying_questions` instead. A self-check pass (`agent/verify.py`) re-validates that evidence against the raw tool output before the report is saved, demoting anything that doesn't check out.

Both are evaluated against an **independent reference pass** (`eval/reference_pass.py`) that runs its own install/build/test/audit/secret-scan per repo, kept out of both systems' context, so scoring isn't circular.

The agent is actually run in three configurations on the same repos (`agent/run_agent.py --variant ...`), which is also the evidence behind `CHANGELOG.md`: `no_contract` (tools available, no evidence mandate), `no_selfcheck` (evidence/`tool_call_id` contract, no self-check repair), and `full` (contract + self-check — the shipped agent).

## Tools used (disclosure)

- **Coding agent used to build this project**: Claude Code (Anthropic), used interactively throughout design and implementation.
- **LLM used inside the submitted solution itself**: OpenAI (`OPENAI_MODEL`, default `gpt-5`) via the Responses API, same model for baseline and agent so the comparison isolates tool-use/verification rather than model capability.
- **Sandboxing**: Docker (see "Safety" below).
- **Eval**: `scipy.stats.spearmanr` for rank correlation; everything else is stdlib + `pydantic`.

## Known limitations / main failure mode

- **Language scope**: full tool support for Python and JS/TS; anything else (Rust, Go, Java, ...) falls back to a line-count heuristic instead of a real linter/audit. This was a deliberate cut to keep the sandbox image and debugging surface bounded for a solo 3-day build.
- **Sandbox residual risk**: commands run inside a resource-limited, non-root, credential-free Docker container with an argv-only, verb-allowlisted executor — but a malicious `postinstall`/`pip install` script could still make outbound network calls during dependency installation *inside* that container. Hardening this further (an egress allowlist, gVisor/Firecracker-level isolation) is the natural next step, not something this weekend build attempts.
- **Observed failure mode**: the model cites tool evidence by an invented, human-readable pseudo-id (e.g. `"functions.run_command:pip_install"`) instead of the real opaque `call_id` it was actually given — even under an explicit contract requiring exact citation. The evidence itself is usually genuine; only the label is wrong. See `CHANGELOG.md`'s Iteration 3 for how this was found (a naive exact-match self-check demoted *100% of tool-backed red flags* across all 8 repos on the first run) and fixed (search every tool result for the evidence, repair the citation, only demote if the evidence appears nowhere).

## Hot take

Don't verify a model's citations by checking if it followed your citation format — verify by independently searching for whether the underlying claim is true. See `CHANGELOG.md`'s closing entry.

## Safety

Consequential actions (running an unfamiliar repo's own build/install/test tooling) are gated behind a single explicit `--enable-sandbox-execution`-style decision documented in `REPRODUCE.md` (not a per-command prompt, which would make an 8-repo eval run un-reproducible hands-off), executed inside a throwaway, resource-limited, non-root Docker container with no host credentials and no live bind-mount of the repo. If Docker isn't available, the agent automatically falls back to static-analysis-only tools rather than failing closed. See `agent/sandbox.py` for the full implementation.
